# Rulebook

The rulebook is the set of decisions a data space has made, written down. The DSSC
Blueprint asks for one directly (`DSSC-TRF-01`) and then, across nine building blocks,
repeatedly requires that a specific decision be *taken* and *recorded here* — which
protocols are accepted, which events are logged, what the minimum metadata set is, how
policy conflicts resolve, who may access the logs. Those rows cannot be closed by code.
They are closed by this section.

## What this is, and what it is not

**It is not documentation of the implementation.** That is [Services](../services/connector.md),
which describes the code as committed. This section states what participants in a
deployment of this platform are required to do and what the platform guarantees in return.
The two are meant to be read together: a rule here without an enforcement point in the code
is a rule nobody keeps.

**It is not a contract.** A real deployment layers its own legal agreements, its own
participation criteria and its own domain rules on top. The service agreements in
`services/identity-registry/seed/agreements.dev.yaml` are the machine-readable hook for
that; this section is the technical and governance baseline they attach to.

**It is a default, and it is overridable.** Every rule here is either a property of the
code (in which case changing it means changing code) or a deployment decision (in which
case a deployment may decide otherwise, and should record that it did). Each page marks
which is which.

## Honesty rule

Each rule carries an **enforcement status**:

| Marker | Meaning |
|---|---|
| **Enforced** | Code refuses the violating case, and a test covers it |
| **Partly enforced** | Code refuses some violating cases and not others; the status says which |
| **Declared** | The rule is a decision, not a check — nothing could enforce it automatically |
| **Not enforced** | The rule is stated, the code does not currently keep it. Carries a link to the defect task |

**Those four, and no synonyms.** Nuance goes after a comma — "Enforced, untested" and
"Enforced, with a declared deviation" are both *enforced*, and the qualifier is for a reader.
The marker itself is what an assessor filters on, so a page reading "Partially enforced" while
six others read "Partly enforced" is not a finer distinction, it is a value nobody can grep
for. `ds-conformance` reports anything outside the four as an `invalid-status` problem, so a
synonym is caught rather than quietly bucketed into the nearest allowed marker.

A rulebook that overstates enforcement is worse than no rulebook, because it converts a
known gap into an unknown one. Where the platform does not currently keep a rule, that is
recorded here rather than in a separate place a reader might not reach. The open items are
tracked as issues (ADR-0012).

## The statuses on these pages are claims, and they are measured

Every status below is **an assertion by whoever wrote it**. What says whether the
assertion has anything behind it is [Conformance status](status.md), regenerated by
`task rulebook:status`.

**A rule is *evidenced* when a test declares itself as the check for it** —
`@pytest.mark.rule("D-15")`, JUnit `@Tag("rule:A-11")`, a `ds-e2e` flow's `rules`
attribute, a Playwright title tag. The marker lives on the test, so it moves with a
rename and vanishes with a deletion, and a rule reading **Enforced** that no test names
is reported as `unevidenced`. See
[docs/development/conformance.md](../development/conformance.md).

**This is the second attempt, and the first one is why the design is this way.** A
`rules.json` projection parsed these pages into ids, statuses and cited evidence, and was
removed on 2026-08-09 because measuring it showed **79% of the rules marked *Enforced*
cited no evidence at all** — 90 of 113 — while the 28 citations that did exist resolved
only to files, never to a check. It turned hand-written claims into counted, published,
machine-readable hand-written claims, and the counts read as measurement when they were
not. The conclusion recorded at the time was that the thing to build is *not a parser*:
it is a rule that **may not say *Enforced* without citing evidence that runs**.

So the citation moved to the test, and the status column became derivable rather than
asserted. What that changed, measurably: every rule claiming enforcement now names at
least one test node, except one — `X-8`, which is enforced by the celine `dataset-api`
outside this repository, and the report says so rather than borrowing the mock's tests to
look complete.

**What it still does not tell you.** It measures *linkage*, not correctness: a marker
means a test node exists and names the rule, not that the node passes. Whether the suites
are green is [testing.md](../development/testing.md)'s answer, and the two questions are
deliberately kept apart.

## Changing a rule

1. Change the page. Every rule states whether it is a code property or a deployment
   decision; a code property cannot be changed here alone.
2. If the rule has an enforcement point, change it in the same commit, and put the rule's
   marker on the test that is the check — `@pytest.mark.rule("<id>")` or its equivalent for
   the layer. A rule and its check drifting apart is the failure mode this whole section
   exists to prevent; the marker is what makes the drift visible instead of arguable.
   Then run `task rulebook:status` and commit the regenerated [status page](status.md).
3. If the rule binds participants operationally, it belongs in a service agreement as well:
   `services/identity-registry/seed/agreements.dev.yaml` plus `seed/content/*.md`, then
   `ir-cli agreement import`. Acceptance is recorded per participant and is visible at
   `GET /agreements/{id}/acceptances`.
4. Note the change in [Scope and deviations](scope-and-deviations.md) if it introduces a
   departure from either blueprint.
