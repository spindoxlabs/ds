# Conformance measurement

How the platform answers *what is done and what is not* without anybody deciding
it by hand each time.

[`docs/rulebook/status.md`](../rulebook/status.md) is generated by
`task rulebook:status` from four inputs, all of them files in this repository:

| Input | Supplies |
|---|---|
| `docs/blueprints/**` | the requirement universe — every `\| ID \| Requirement \| Force \| Source \|` row |
| `docs/rulebook/*.md` | the rules, their pages, and the enforcement status each **claims** |
| the test sources | which tests declare themselves as evidence for which rule |
| `docs/rulebook/coverage.yaml` | the judgement calls: declined, accepted-and-unmet, or answered at page level |

It reads markdown and source. It never runs a suite, never starts a stack and
never needs another unit's virtualenv, so **the same commit gives the same
answer on every machine**. That is the property this replaces a hand-written
assessment for.

## What it measures, and what it does not

**It measures linkage.** A rule is *evidenced* when a test node names it. It is
not a claim that the node passes — that is the test runner's answer, and
[testing.md](testing.md) is where the layers and what each proves are set out.

What this can say, and no hand-written status column can, is whether a claim has
a runnable referent **at all**. The previous attempt at this — a `rules.json`
projection, deleted 2026-08-09 — counted the claims instead, and measuring it
showed 79% of the rules marked *Enforced* cited no evidence whatsoever. The
lesson recorded at the time was *"the thing to build is not a parser: it is a
rule that may not say Enforced without citing evidence that runs."* This is
that, with the citation living on the test rather than in the prose.

## Declaring a test as evidence

The marker goes **on the test**, so it moves with a rename, disappears with a
deletion, and appears the moment somebody writes a new check. That is what makes
the status column derivable instead of asserted.

=== "Python"

    ```python
    @pytest.mark.rule("D-15")
    def test_an_explicit_opt_out_beats_the_wildcard() -> None: ...
    ```

    The marker is registered in each unit's `pyproject.toml`, so a typo warns
    rather than silently evidencing nothing. One test may name several rules.
    A marker on a class or in `pytestmark` covers everything under it.

=== "Java"

    ```java
    @Test @Tag("rule:A-11")
    void sustainedSilenceTerminates() { … }
    ```

    `@Tag` is JUnit's own mechanism — `gradle test` can select on it — so the
    marker is useful independently of this report.

=== "e2e flow"

    ```python
    class ConsentWithdrawalFlow(BaseFlow):
        name = "consent-withdrawal"
        rules = ("A-12", "D-17", "P-18")
    ```

    A flow is one named journey, so the declaration belongs on the class. The
    report cites the flow **name**, which is what `task e2e:all` prints — so a
    reader can run exactly the evidence named.

=== "Playwright"

    ```ts
    test('a viewer cannot write @rule:P-12', async ({ page }) => { … })
    ```

    Playwright selects on title tags with `--grep`, same argument as `@Tag`.

The report shows the layers separately rather than one total, because they do
not prove the same thing: a rule evidenced only by a unit test is evidenced
against a mock, and one evidenced by an e2e flow is evidenced against the
platform.

## The verdicts

The claimed status and the evidence count give a closed truth table, and every
cell says something different:

| Claimed | Evidence | Verdict | Meaning |
|---|---|---|---|
| `Enforced` / `Partly enforced` | ≥1 | `evidenced` | the claim has a runnable referent |
| `Enforced` / `Partly enforced` | 0 | **`unevidenced`** | the claim is prose. This is the finding |
| `Declared` | 0 | `consistent` | correct by definition — nothing could check it |
| `Declared` | ≥1 | `understated` | tests exist; the row may be upgradeable |
| `Not enforced` | 0 | `consistent` | claims nothing, owes nothing |
| `Not enforced` | ≥1 | **`contradicted`** | the row says no and the tree says yes |

`unevidenced` is **not** an accusation that a rule is unimplemented. It says the
repository cannot demonstrate the link — a different and more useful statement.

`Declared` owes no evidence and must keep owing none: demanding a test for it
would push authors to downgrade honest decisions, which is the opposite of what
the [honesty rule](../rulebook/index.md#honesty-rule) wants.

## Blueprint coverage

The second axis: is every row this data space is bound by accounted for.

Which rule answers which row is **derived** wherever the rulebook already writes
it — `C-1 … (DSSC-PUB-05)`, `C-17 … (PUB-19, -23, -26)`. Keeping a second copy
of that in a manifest is how the deleted policy matrix drifted, so it is read
off the rule text instead.

`coverage.yaml` carries only what no file states on its own:

```yaml
dispositions:
  DSSC-XCT-27:
    state: out-of-scope
    note: "this platform cannot prove effective anonymisation"
  DSSC-AUP-06:
    state: open
    note: "the validity window needs a date operand bound in the EDC first"
  DSSC-PUB-01:
    state: covered
    pages: [catalogue-and-metadata]     # topic addressed; no rule named yet
```

**`covered` has two strengths and the report keeps them apart.** `rules:` makes
the row inherit that rule's verdict, so a rule nothing tests leaves the row
visibly unanswered. `pages:` asserts only that a page addresses the topic — it
is the granularity the rulebook's own *Blueprint rows* prose has, it carries no
evidence, and it can never read as done. Sharpening a page-level row to a named
rule is ordinary work the report lists.

A row in none of the three is `unassessed`: nobody has looked at it. That is a
state rather than a silence, and it is counted.

`may` and `recommended` rows are parsed and counted but never demanded —
declining an optional row owes nobody an explanation, silently dropping a `must`
owes everybody one.

## Commands

```bash
task rulebook:status              # regenerate docs/rulebook/status.md
task rulebook:check               # fail if the committed page is stale
task rulebook:unevidenced         # the rules that claim enforcement and name no test
task rulebook:rule RULE=A-11      # one rule, and every test that evidences it
task rulebook:test                # the tool's own suite
```

`status.md` is **committed**, so a change in what the repository can demonstrate
shows up in a diff. Regenerate it in the same commit as any change to a rule, a
marker, or the manifest — the same discipline
[the rulebook already asks for](../rulebook/index.md#changing-a-rule).

**`rulebook:check` runs in CI** as the `rulebook-current` job of
`.github/workflows/compliance.yml`, so forgetting that regeneration is now a red
build rather than a silent drift. It gates on **staleness only** — see the
`--strict` limit below.

## Limits, stated rather than hidden

- **A marker means a node exists, not that it passes.** A marker on a skipped or
  broken test still counts as linkage.
- **Static parsing.** A marker reached only through a runtime-generated
  decorator is invisible. A test file that will not parse is *reported* rather
  than skipped — an earlier version swallowed the error and returned nothing,
  which read identically to "this file evidences no rule".
- **`services/dataset-api-mock` is deliberately not evidence**, and this page is
  where that exclusion is recorded: it is a stand-in, not a deployed component,
  and the real data plane is the celine `dataset-api`. This
  is why `X-8` — *a query result is bounded* — reads `unevidenced`: it is
  enforced by the celine `dataset-api`, which lives outside this repository. The
  report says so rather than borrowing the mock's tests to look complete.
- **`--check` compares the measurement, not the header.** The page's `Generated
  … from …` line names the commit the render ran at, which for a committed page
  is always the commit *before* it — and writing the page dirties the tree, so a
  re-render at the same `HEAD` says `X-dirty` against the `X` on disk. Comparing
  that line made the check unsatisfiable in both directions rather than strict
  ([#18](https://github.com/spindoxlabs/ds/issues/18)); it is excluded, and the
  header stays for a reader who wants to know roughly how old the numbers are.
  Everything else on the page is compared byte for byte.
- **Staleness is a gate; the findings are not.** `rulebook:check` fails CI when
  the page no longer matches the tree, which is a question with one right
  answer. `--strict` — which fails on an unevidenced or contradicted rule, or a
  structural problem — still runs nowhere, deliberately: those are findings to
  read and argue with, and a rule honestly marked `Declared` must never be
  something CI pushes an author to downgrade.
